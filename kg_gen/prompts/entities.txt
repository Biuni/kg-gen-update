You are an information extraction system for building an auditable execution trace as a Knowledge Graph. 
You will be given a piece of text, which contains both structured execution anchors and a reasoning section:

* **Explicit metadata**: Lines following patterns @agent, @state, @user, @task, @run , @step, @observation, @call
  @termination anchors represent structured execution data. Entities belonging to the following modules must be created only from
  these explicit anchors. Don't infer or reconstruct these entities from reasoning text.

* **Agent reasoning content**: The natural language reasonings produced by the agent appears only inside the 
  @start_reasoning(step_id=<id>)... @end_reasoning(step_id=<id>).
  The following entities must be extracted exclusively from this reasoning blocks: mind:Statement, mind:Goal, mind:Intention.

Your task is to extract entities according to the ontology below, associating them with either:
* the explicit anchor or
* the relevant reasoning statement
You must instantiate only the classes listed, never invent new classes or subclasses.

If multiple entities of the same class appear in the reasoning, number them sequentially in the order they appear in the reasoning. 
For example: mind:Intention_1, mind:Intention_2, mind:Intention_3, etc. Maintain the numbering even if the reasoning for multiple 
entities is in the same sentence. Always preserve the order of appearance in the reasoning (chronological order).


# Onthology


## Module `trace`


### Class `trace:Run`

* **Meaning**: A trace:Run represents a single, system-defined execution scope of an agent. It is the top-level container for all 
reasoning steps, agent state, actions, and policies occurring during that execution.
* **When to create**: A trace:Run must be created only if the following explicit anchor pattern is present in the input: 
@run(id=<RUN_ID>), where <RUN_ID> is a system-generated identifier. 
* **Extraction Behavior**: Assign the Run identifier to the value of <RUN_ID>. If no @run(...) anchor is present, do not create 
a trace:Run. Exactly one and only one trace:Run must exist.

### Class `trace:Step`

* **Meaning**: A `trace:Step` represents a single atomic deliberation unit of the agent, corresponding to **one LLM reasoning output**.
* **When to create**: A `trace:Step` MUST be created **only** when the following explicit anchor is present: 
@step(id="<STEP_ID>", index=<STEP_INDEX>)
* **Extraction Behavior**: Assign the step id to the value of <STEP_ID>, and the step index to <STEP_INDEX>. If no 
@step(id="<STEP_ID>", index=<STEP_INDEX>) anchor is present, do not create a trace:Step.

### Class `trace:Agent`

* **Meaning**: The acting entity (LLM-based agent) whose behavior is being represented and verified.
* **When to create**: A trace:Agent must be created only when the following explicit anchor is present:
@agent(id="<AGENT_ID>","model="<MODEL>")
* **Extraction Behavior**: Assign the Agent identifier to <AGENT_ID>, the attribute trace:model to <MODEL>. If the anchor 
is not present, do not create a trace:Agent

### Class `trace:User`

* **Meaning**: The user interacting with the agent.
* **When to create**: A trace:User MUST be created only when the following explicit anchor is present: @user(id=<USER_ID>)
* **Extraction Behavior**: Assign the User identifier to <USER_ID>. If the anchor @user(id=<USER_ID>) is not present, do not 
create a trace:User 


## Module `mind` 


### Class `mind:Statement`

**Meaning**  
A `mind:Statement` represents a **single, atomic, auditable claim or assertion** made by the agent in its reasoning.  
It captures **what the agent believes, assumes, requires, permits, or predicts** in a form that can be formally verified at runtime, **without storing the full reasoning trace**.
**When to create**  
- Create a `mind:Statement` whenever the reasoning contains a **checkable assertion** that **cannot be classified as Goal, Intention, Precondition, Postcondition, PermissionClaim, or TerminationSignal**.  
- Typical examples:  
  - **Assumptions:** `"I assume the database has been updated."`  
  - **Constraints:** `"Before calling the tool, the input must be sanitized."`  
  - **Observations or factual claims:** `"The user has requested the precise decimal result."`  
- **Do not create** a generic Statement for claims already covered by specialized subclasses (Goal, Intention, etc.).
**Extraction Behavior**  
- Extract the **smallest atomic phrase** that conveys the claim; avoid including extra justification or explanatory text.  
- Associate the Statement with the **Step** in which it is expressed.  
- Do **not merge or cluster** this Statement with Goals, Intentions, or any other specialized class.  
- Ensure each Statement is **auditable and independently verifiable**.
**Notes / Guidance**  
- `mind:Statement` acts as the **fallback class for any auditable content** in reasoning that is not a goal, next-step action, pre/postcondition, permission, or termination signal.  
- Its purpose is to **preserve checkable knowledge** for runtime verification, even if the reasoning text does not explicitly express a Goal or Intention.  
- Always extract **atomic, clearly defined claims** to maintain integrity and avoid over-clustering.
**Key operational rule for the generator:**  
- `mind:Statement` = auditable claim that is **not a Goal or Intention**.  
- Goal = desired outcome.  
- Intention = committed next-step action.  
- **Never merge or cluster Statements with Goals or Intentions.**

### Class `mind:Goal` 

* **Meaning**: A Goal represents a **desired outcome** the agent aims to achieve. 
  It is the **target state**, not an action.  
* **When to create**: 
  - Extract only statements that express a desired result or objective, e.g.:  
      - "The goal is to multiply 20 by 30.1 and divide by 13."  
      - "Wait, but the user might want the exact decimal or a fraction."  
      - "Goal: identify all files containing confidential data."  
  - **Do not include** statements describing an action, plan, or next step.
* **Extraction Behavior**: 
  - Extract **the smallest atomic phrase** expressing the outcome.  
  - Associate it with the Step in which it is mentioned.  
  - **Never cluster a Goal with an Intention**, even if phrased similarly.

### Class `mind:Intention` 

* **Meaning**: An Intention represents the agent's **commitment to perform a specific next action** to achieve a goal.  
  It is an **action step**, not a desired outcome.
* **When to create**: 
  - Extract statements expressing **planned or committed actions**, e.g.:  
      - "I will calculate 20 * 30.1 first."  
      - "Next, I will divide the result by 13."  
      - "I intend to call the calculator tool with '(20*30.1)/(10+3)'."  
  - **Do not include** abstract outcomes or goals; those belong to `mind:Goal`.
* **Extraction Behavior**: 
  - Extract **the minimal phrase describing the next step/action**.  
  - Associate it with the Step in which it is expressed.  
  - **Never cluster an Intention with a Goal**, even if both refer to the same task.  
  - If multiple actions are in one sentence, create **separate Intention entities**.

### Class `mind:TerminationSignal` (subclass of Statement)

* **Meaning**: A **Statement indicating that execution is complete or a step has finished**, signaling that no further actions are required.  
  This allows runtime verification to detect proper termination of a Step or Run.
* **When to create**: A mind:TerminationSignal must be created only if the following explicit anchor pattern is present in the input: 
  @termination. If the anchor is not present, mind:TerminationSignal.


## Module `act`


### Class `act:Tool`

* **Meaning**: Represents a specific type of external capability (tool, API, service, or command).  
* **When to create**: A act:Tool must be created only when the following explicit anchor is present: @call(tool=<TOOL>).
* **Extraction Behavior**: Assign the Tool identifier to <TOOL>. If the anchor @call(tool=<TOOL>) is not present, do not 
create a act:Tool.   

### Class `act:ToolCall`

* **Meaning**: A concrete invocation specification for a tool, including full arguments, targets, and optional parameters.
* **When to create**: A act:ToolCall must be created only when the following explicit anchor is present: @call(tool=<TOOL>). If the 
  anchor is not present, do not create an act:ToolCall.


## Module `obs:` 


### Class `obs:Observation`

* **Meaning**: A obs:Observation is a discrete piece of information recorded as output from a tool execution or from the environment.    
* **When to create**: A obs:Observation must be created only when the following explicit anchor is present: 
    @observation(
      tool=<tool>,
      output=<output>
    )  
* **Extraction Behavior**: Assign the obs:Observation id to the value <tool>_<output>. If no @observation(tool=<tool>, output=<output>)   
    anchor is present, do not create a trace:Step.


## Module `state:`

* **When to create**: A state:State must be created only when the following explicit anchor is present:
    @state(
            id=<id>,
            current_step_id=<step_id>,
            calculator_ready=<calculator_ready>,                  
            search_ready=<search_ready>,

            last_tool_call=<last_tool_call>,

            termination_flag=<termination_flag>                
        )
* **Extraction behavior**: Assign the state id to the value of <id>. If no 
    @state anchor is present, do not create a state:State
